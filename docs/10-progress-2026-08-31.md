# 進捗ログ 2026-08-31

## 8月30日の実地テスト結果

接続中の時計で計測を終了し、スマホアプリは開かない状態で通知・履歴の自動受信を確認した。

### 観測結果

- 時計とスマホが接続済みの状態で、時計の計測終了ボタンを押した。
- 10分以上待っても、スマホには通知が届かず、履歴も自動では反映されなかった。
- 最終的にスマホアプリを手動起動すると、記録を取り込めた。
- これは、8月29日の「機内モード中に終了した記録が7分後に自動通知された」試験とは異なる失敗結果である。

従って、8月29日時点で確認した自動回復は有効な1回の実測結果ではあるが、接続復帰・接続中のいずれでも安定して自動受信できることは、まだ確認できていない。

## ログから分かること

8月31日に取得したスマホログには、以下の記録がある。

```text
13:58:44 *job*r/com.totonoi.sauna/androidx.work.impl.background.systemjob.SystemJobService
13:58:44 ActivityManager: sync unfroze ... com.totonoi.sauna
```

これは、追加したWorkManagerの定期フォールバック自体はOSによって起動されていることを示す。ただし、この採取ログには対象セッションの時計側送信時刻と、アプリ側の`SessionSyncListener` / `SessionImportWorker`の詳細ログが含まれないため、失敗時に次のどこで止まったかは確定できない。

- 時計からの即時メッセージ送信
- 時計からの履歴用`DataItem`登録
- Google Play ServicesによるData Layer配送
- スマホの`WearableListenerService`またはWorkManagerによる保存・通知

## 根本原因として確認した実装上の欠陥

時計側の`SessionSyncSender`は、従来、次の順で実行していた。

1. 接続済みノードへ`MessageClient.sendMessage()`で即時通知を送信
2. 成功後に`DataClient.putDataItem()`で履歴用`DataItem`を登録

`MessageClient`は接続状態の変化やData Layer内部の一時的な状態により失敗し得る。一つでも例外が発生すると、処理全体が終了し、後続の履歴用`DataItem`が登録されない構造だった。

この場合、スマホ側は取り込むべき`DataItem`を持たないため、以下のすべてが失敗する。

- `WearableListenerService`によるバックグラウンド受信
- WorkManagerによる定期回収
- 手動起動前の履歴表示

「接続済みで終了しても10分以上届かない」という今回の症状と整合する。これは確定した一般的な実装不備であり、端末の省電力制御だけに原因を限定しない。

## 実施した修正

[SessionSyncSender.kt](../wear/src/main/kotlin/com/totonoi/sauna/wear/session/SessionSyncSender.kt)を変更した。

- 先に`DataClient.putDataItem(...).setUrgent()`を実行し、履歴同期対象を必ずData Layerへ登録する。
- `MessageClient`の即時通知送信は後段へ移動する。
- ノード単位の即時送信失敗は`runCatching`で記録し、他ノードへの送信や登録済み`DataItem`の同期を中断しない。

これにより、即時通知に失敗しても、Data Layerの遅延同期とスマホ側WorkManagerフォールバックが機能する前提条件を維持できる。

## 次回の確認手順

1. スマホアプリを一度起動してホームへ戻す。強制停止はしない。
2. 時計・スマホが接続済みの状態で短時間計測を終了する。
3. 時計ログで、以下の順序を確認する。

   ```text
   SessionSyncSender: Submitting session ... to Data Layer
   SessionSyncSender: Session ... accepted at wear://...
   SessionSyncSender: Sending notification ... to ... node(s)
   ```

4. スマホアプリを開かず、通知と履歴反映を15分間確認する。
5. 同じ手順を、計測終了時に機内モードで切断したケースでも行う。
6. 失敗時はスマホ側で`SessionSyncListener`、`SessionImportWorker`、`NotificationManagerService:post:com.totonoi.sauna`を取得し、時計側の上記ログと照合する。

## 現在の判定

- 接続中に終了した直後の即時通知: 過去に成功実績はあるが、再現性は未確定。
- 切断中に終了した記録の復帰後自動受信: 1回成功、1回以上の失敗があり、再現性は未確定。
- 記録の喪失防止: 今回の送信順序修正により、即時通知の一時失敗が永続同期の登録を止める欠陥は解消した。
- 次の実地テストでは、通知到達時間だけでなく、時計側で`DataItem`受理ログが出ていることを合格の前提条件として扱う。

## 追補: 8月31日後半の再テストと追加修正

### 追加テスト結果

送信順序修正後に、再度「接続が切れた状態で計測終了ボタンを押し、接続回復後にスマホアプリを開かず10分以上待つ」テストを行った。

- 受信完了通知は表示されなかった。
- 10分以上放置してもスマホ履歴へ自動反映されなかった。
- 最終的にスマホアプリを手動起動して取り込む必要があった。

このため、`DataItem`を先に投入するだけでは、接続断後の復帰時自動同期は安定しないことが判明した。

### 追加で判明した問題

時計側ログに、追加したWear側`SessionSyncListenerService`がGoogle Play Servicesから起動されず、権限拒否されている記録が出ていた。

```text
Permission Denial: Accessing service com.totonoi.sauna/.wear.session.SessionSyncListenerService
from pid=6523, uid=10108 requires com.google.android.gms.permission.BIND_LISTENER
```

つまり、接続復帰時に未送信キューを再送する目的で追加したWear側リスナーが、Manifest上の`android:permission="com.google.android.gms.permission.BIND_LISTENER"`指定により、Wear OS上のGMSからバインドできない状態だった。

これは再送機構が動いていない直接原因であり、前回修正の重大な不備である。

### ACK方式への変更

さらに、時計側で`DataClient.putDataItem()`が成功した時点で未送信キューから削除すると、スマホ側で実際に保存・通知されたかを保証できない問題が残っていた。

そこで、同期完了の判定を「時計側DataItem受理」ではなく「スマホ側保存後のACK受信」に変更した。

- 時計側は計測終了時にセッションIDを未送信キューへ追加する。
- 時計側は`DataItem`を投入しても、未送信キューからは削除しない。
- スマホ側は`SessionSyncListenerService`または`SessionDataLayerImporter`でセッション保存後、時計へ`/sauna/session/ack`メッセージを返す。
- 時計側はACKを受け取って初めて未送信キューから削除する。
- 接続復帰時、Wear側`SessionSyncListenerService`が未送信キューを読み出し、保存済みセッションを再送する。
- 再送時は`sync_attempt_ms`を更新して同じセッションIDの`DataItem`でも再配送されるようにする。

### 実施した追加修正

- [DataLayerKeys.kt](../shared/src/main/kotlin/com/totonoi/sauna/shared/sync/DataLayerKeys.kt)

  - `KEY_SYNC_ATTEMPT_MS`を追加。
- [SessionSyncSender.kt](../wear/src/main/kotlin/com/totonoi/sauna/wear/session/SessionSyncSender.kt)
  - DataItemに`sync_attempt_ms`を入れ、再送ごとに更新。

  - Wear側に未送信セッションIDを保存するキューを追加。
- [SessionRetrySyncer.kt](../wear/src/main/kotlin/com/totonoi/sauna/wear/session/SessionRetrySyncer.kt)
  - 未送信IDからRoom上のセッションを読み出して再送する処理を追加。
- [SessionSyncListenerService.kt](../wear/src/main/kotlin/com/totonoi/sauna/wear/session/SessionSyncListenerService.kt)
  - 接続復帰時に再送を実行。
  - スマホからのACK受信時に未送信キューから削除。
- [SessionAckSender.kt](../mobile/src/main/kotlin/com/totonoi/sauna/mobile/sync/SessionAckSender.kt)
  - スマホ側から時計へ保存完了ACKを送る処理を追加。
- [SessionSyncListenerService.kt](../mobile/src/main/kotlin/com/totonoi/sauna/mobile/sync/SessionSyncListenerService.kt)

- [SessionDataLayerImporter.kt](../mobile/src/main/kotlin/com/totonoi/sauna/mobile/sync/SessionDataLayerImporter.kt)
  - WorkManagerまたは手動起動時の取り込み後にもACK送信。
- [wear/src/main/AndroidManifest.xml](../wear/src/main/AndroidManifest.xml)
  - Wear側`SessionSyncListenerService`から`android:permission="com.google.android.gms.permission.BIND_LISTENER"`を削除。

### 現時点の判定更新

- 8月29日の自動通知成功は有効な実測結果だが、安定動作の証明ではなかった。
- 8月30日および8月31日の失敗により、従来設計は実地運用に耐えないと判断する。
- 原因は単一ではなく、送信順序の脆弱性、送信完了判定が早すぎること、Wear側再送リスナーの権限設定ミスが重なっていた。
- 現在はACK方式と接続復帰時再送を導入し、少なくとも「スマホ保存確認前に時計側が送信済み扱いにする」問題は解消した。
