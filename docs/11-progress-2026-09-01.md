## 接続復帰テスト

### 実地結果

接続断中に計測を終了した後、時計・スマホの接続を復帰させ、スマホアプリを開かずに待機した。

- 接続回復後、およそ5分で受信完了通知が届いた。
- これは、接続断中に完了した記録がアプリ未起動状態でも最終的に届くことを示す。
- ただし5分の遅延は利用体験として長く、即時同期としては合格としない。

### ログで確認できたこと

時計ログには、`com.totonoi.sauna.wear.session.SessionSyncListenerService`がGoogle Play Servicesから`bound-service`として起動された記録がある。

```text
Start proc ... com.totonoi.sauna ... for bound-service
{com.totonoi.sauna/com.totonoi.sauna.wear.session.SessionSyncListenerService}
```

8月31日に確認された`BIND_LISTENER`の権限拒否は解消済みである。一方、保存済みログにはアプリ固有タグの詳細が不足するため、今回の到達が「接続復帰時の能動再送」「Data Layer自身の遅延配送」「スマホ側WorkManager」のどれによるものかは断定できない。

### 今後の同期設計

時計側では、次の仕組みを実装済みである。

- 計測終了時にセッションIDを未送信キューへ保存する。
- `DataItem`を先に登録し、即時通知の失敗で永続同期が止まらないようにする。
- スマホが保存後にACKを返すまで、時計側は未送信IDを削除しない。
- Wear側`SessionSyncListenerService`の接続復帰イベントで、未送信キューのセッションを即時、5秒後、20秒後の最大3回再送する。接続直後のData Layer初期化が完了していない場合を吸収するためであり、常駐ループにはしない。
- 再送時は`sync_attempt_ms`を更新し、同一セッションIDのDataItemも変更イベントとして再配送を促す。

次回は、時計側の`WearSessionSyncListener`、`SessionRetrySyncer`、スマホ側の`SessionAckSender`を含めてログを採取し、接続復帰からACKまでの所要時間を計測する。判定は通知表示だけでなく、ACK受信まで確認する。

## 計測履歴の削除機能

スマホアプリに履歴削除を実装した。

- 詳細画面右上の`削除`を選択する。
- 確認ダイアログを表示してから削除する。
- 削除対象はスマホのRoomデータベース上の記録であり、時計側に保存された元データは保持する。
- 削除済みセッションIDをスマホ内に保持し、時計側Data Layerに残る同一IDの記録が後の同期やアプリ再起動で復元されないようにした。

### 一覧からの選択削除

計測履歴の一覧画面から、複数の記録を選択して削除できる機能を追加した。

- 一覧上部の`選択`で選択モードへ切り替える。
- 選択モードでは、各履歴カードのチェックボックスまたはカードのタップで選択状態を切り替える。
- `全選択`と`選択解除`で対象をまとめて操作できる。
- `削除`は選択件数を示す確認ダイアログを表示し、確定後にすべての選択済みIDを削除する。
- `完了`または戻る操作で選択モードを終了する。
- 一括削除にも削除済みIDの保持を適用するため、時計から同一セッションが再同期されてもスマホ履歴には復元されない。

`HistoryViewModel.deleteSessions()`が、選択した各IDを削除済みストアへ記録してからRoomデータベースから削除する。

## 履歴記録のWebサービス化: 初期検討

現状は時計・スマホのRoomデータベースのみへ記録している。そのため、両アプリをアンインストールすると履歴が失われ、端末変更や複数端末への同期もできない。将来リリースでは、クラウドを正本にしたアカウント単位の履歴同期が必要である。

### 採用方針

アプリはオフライン優先を維持する。

1. 時計で計測終了時にローカルへ即時保存する。
2. Data Layerでスマホへ同期する。
3. スマホはローカルDBを表示の一次データとして使う。
4. スマホは通信可能時にクラウドAPIへ未同期セッションをアップロードする。
5. サーバーはセッションIDを冪等キーにして保存する。
6. ログイン済みの別スマホや機種変更後は、サーバーから履歴を取得してローカルDBへ反映する。

この構成なら、サウナ施設でオフラインになっても計測・閲覧・Wear同期を継続できる。クラウド同期失敗は後で再試行でき、端末側の計測記録を失わない。

### 最小API案

- `POST /v1/sessions`: セッションをID指定で作成または更新する。重複要求でも同じレコードを返す。
- `GET /v1/sessions?updatedAfter=...`: 差分同期用の一覧取得。
- `DELETE /v1/sessions/{id}`: アカウント単位で履歴を削除する。
- `POST /v1/devices`: 端末登録と同期状態の管理。

送信データは現在の`SaunaSession`を基礎にし、サーバー側には`userId`、`createdAt`、`updatedAt`、`deletedAt`、`schemaVersion`を追加する。削除は端末ごとの単純なローカル削除ではなく、全端末に伝播できる論理削除として扱う。

### 認証・個人データ

心拍数は健康関連の個人データとして扱う。リリース版では以下を必須条件とする。

- 匿名ではなく、OAuth/OpenID Connect等のアカウント認証を使う。
- 通信はHTTPSのみとし、保存データは暗号化とアクセス制御を行う。
- 利用者が履歴を一括削除できる機能と、削除方針を用意する。
- データの利用目的、保存期間、第三者提供の有無をプライバシーポリシーで明示する。

### 段階的な実装計画

1. スマホにアップロード待ち状態・最終同期時刻・再試行を持つ同期キューを追加する。
2. 認証と`POST /v1/sessions`だけを持つ最小バックエンドを構築する。
3. 端末変更用の`GET /v1/sessions`と差分同期を追加する。
4. クラウド削除と端末間の削除同期を追加する。
5. 運用監視、バックアップ、レート制限、プライバシーポリシーを整備して公開する。

バックエンド基盤は、初期開発速度を優先するならFirebase Authentication + Cloud Run/Firestore、API・データベースの移植性を重視するならCloud Run + PostgreSQLを候補とする。現時点では認証方式、想定ユーザー数、課金モデル、データ保持期間が未確定のため、どちらかを確定採用しない。
